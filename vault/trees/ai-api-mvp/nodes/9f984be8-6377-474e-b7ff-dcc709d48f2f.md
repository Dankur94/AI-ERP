# Tech-Stack — Gesetzte Entscheidungen

Stand: 2026-05-06. Alle Entscheidungen einzeln diskutiert und bestaetigt.

## Prinzip

Fast alles aus bestehenden APIs. Kosten-optimiert fuer den Start.
Ein-Mann-Team + Claude Code → jede Wahl optimiert fuer Produktivitaet und Zuverlaessigkeit.

## Fundament (gesetzt)

| Entscheidung | Wahl | Warum | Verglichen mit |
|---|---|---|---|
| Sprache | **Python 3.12** | AI-Oekosystem, wenig Boilerplate, Type Hints + pyright | Node.js (OpenClaw), Go (Grab), Java (WeChat) |
| Framework | **FastAPI** | Async, Auto-Docs, Pydantic Validation, WebSocket eingebaut | Django, Flask, Litestar |
| Datenbank | **PostgreSQL ab Tag 1** | Echtes Environment von Anfang an, PostGIS fuer spaeter (GPS/Maps), concurrent writes | SQLite (zu klein), MySQL (weniger Features), MongoDB (keine Relationen) |
| Queue | **arq + Redis** | Async-native (passt zu FastAPI), minimal, eine Dependency | Celery (sync in async-Welt), Dramatiq, TaskIQ, Eigenbau |
| Cache | **Redis (ein Store fuer alles)** | Laeuft schon fuer arq — auch fuer Locks, Sessions, spaeter Cache | Memcached (zweiter Server unnoetig) |
| Auth | **Custom JWT (3 Flows)** | Auth ist KERN, nicht outsourcen. 3 User-Typen brauchen 3 verschiedene Flows | Supabase Auth (T3 passt nicht), Auth0 (teuer, Lock-in) |
| AI | **Claude API direkt + Adapter-Pattern** | AI IST die App, kein Wrapper noetig. Haiku (90%) + Sonnet (10%) fuer Kosten | LangChain (Abstraction Hell), LiteLLM (Lowest Common Denominator) |
| Real-Time | **FastAPI WebSocket** | Eingebaut, kein Overhead, 2 Rooms reichen (shop + session) | Socket.IO (Overkill), SSE (nur eine Richtung) |
| Suche | **PostgreSQL FTS** | Schon da (PostgreSQL laeuft), reicht fuer 20-200 Shops | Meilisearch (spaeter bei 500+), Elasticsearch (zu schwer) |
| Frontend | **Vue.js 3 (PWA)** | Chat-UI + Rich Cards, SFC Pattern, schnellstes Laden, Composition API | React (mehr Boilerplate), Svelte (kleine Community), HTMX (keine Rich Cards) |

## Auth — 3 Flows (gesetzt)

| User-Typ | Auth-Methode | Session |
|---|---|---|
| T1 (Developer) | API Key + Secret im Header | Langlebig (Tage) |
| T2 (Shop-Owner) | Email + Passwort → JWT Token | 24h |
| T3 (Endkunde) | Kein Login, Session Token nach QR-Scan, Phone-Verify nur bei Buchung | 1h |

## AI-Routing — 2 Stufen (gesetzt)

Kein Pattern-Match (zu fehleranfaellig). Immer AI, aber das richtige Model:

| Stufe | Model | Wann | Kosten/Call |
|---|---|---|---|
| Standard (90%) | Claude Haiku | Einfache Intents, Buchungen, Info-Fragen | ~$0.0003 |
| Komplex (10%) | Claude Sonnet | Analyse, Strategie, mehrstufiges Reasoning | ~$0.004 |
| Fallback | OpenAI GPT-4o | Nur wenn Claude API down | ~$0.003 |

Haiku erkennt selbst wenn es ueberfordert ist → eskaliert zu Sonnet mit [ESCALATE].

## AI Permission Gate (gesetzt)

Rollenbasierte Tool-Sets. AI darf nur Tools aufrufen die fuer die Rolle erlaubt sind:
- T3: check_slots, create_booking, cancel_own, shop_search, shop_info
- T2: alles von T3 + list_all_bookings, manage_slots, view_revenue, edit_profile
- T1: API-Zugriff gemaess API Key Scope

Policies als YAML: policies/t3.yaml, policies/t2.yaml, policies/t1.yaml

## Queue-Patterns (gesetzt, auf arq gebaut)

4 Patterns die wir auf arq + Redis draufbauen:

| Pattern | Loest | Wie |
|---|---|---|
| Redis Lock | Doppelbuchung verhindern | `redis.lock()` pro Shop bei Booking |
| Saga | Bridge-Module (Booking+Payment) | Status-Machine: pending→confirmed/compensated |
| Lane-FIFO | Chat-Reihenfolge | Lock pro Conversation |
| Idempotency | Kein doppeltes Geld | Redis Key + Stripe Idempotency Key |
