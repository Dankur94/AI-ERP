# Queue pro Entity

Von OpenClaw OC1 — ab Tag 1 eingebaut.

## Was es ist

Jeder Laden (Entity) bekommt seine eigene Warteschlange. Anfragen werden der Reihe nach abgearbeitet.

## Warum

- Verhindert doppelte Buchungen (zwei Kunden buchen denselben Slot gleichzeitig)
- Saubere Isolation: Problem bei Laden A blockiert nicht Laden B
- Keine Race Conditions
- Skaliert natuerlich: mehr Laeden = mehr Queues, nicht mehr Last pro Queue

## Wie

```
Laden A: [Buchung1] → [Buchung2] → [Zahlung1]
Laden B: [Profilaenderung] → [Buchung1]
Laden C: (leer)
```

Jede Queue arbeitet unabhaengig. Reihenfolge garantiert.

## Technisch (gesetzt: 2026-05-06)

- **arq + Redis** (async-native, passt zu FastAPI)
- Aufwand: 1-2 Tage Setup
- Kosten: Redis ~$0-15/Monat

Warum arq statt Celery:
- Celery ist sync → passt nicht zu FastAPI (async)
- Celery braeuchte sync-Versionen aller Funktionen → doppelter Code
- arq: eine Dependency (redis), async-native, simpel

## Structured Key

Queue-Name folgt dem Key-Schema:
```
queue:shop:{shop_id}:default
queue:shop:{shop_id}:booking
queue:shop:{shop_id}:payment
queue:shop:{shop_id}:notify
```

## 4 Patterns (auf arq gebaut)

### 1. Redis Lock (Doppelbuchung)
```python
async with entity_lock(redis, f"shop:{shop_id}:booking"):
    # Nur EIN Booking-Job gleichzeitig pro Shop
```

### 2. Saga (Bridge-Module: Booking + Payment)
```
Booking (pending) → Payment ✓ → Booking (confirmed)
Booking (pending) → Payment ✗ → Booking (compensated) → Rueckgaengig
```

### 3. Lane-FIFO (Chat-Reihenfolge)
```python
async with entity_lock(redis, f"lane:shop:{shop_id}:chat:{conv_id}"):
    # Pro Conversation strikt sequentiell
```

### 4. Idempotency (kein doppeltes Geld)
```python
# Redis Key + Stripe Idempotency Key = doppelte Absicherung
result = await idempotent_execute(redis, f"payment:{booking_id}", charge_fn)
```
