# Von OpenClaw

## Bereits uebernommen

| Prinzip | Wie wir es nutzen |
|---|---|
| OC3 — Channel Adapter | Stripe, FPS, WhatsApp, Google Maps — alles durch Adapter normalisiert. Ein internes Modell. |
| OC4 — Skills als Dateien | T2 Laden kann Verhalten anpassen ohne Code (z.B. Oeffnungszeiten-Regeln als Config) |
| OC5 — Modulare Prompts | Jedes Modul (Booking, Chat) bringt eigenen AI-Kontext mit |
| OC7 — Structured Keys | `shop:module:entity` — Multi-Tenancy im Key-Design von Tag 1 |
| OC8 — Hub-and-Spoke | Ein Gateway, ein Einstiegspunkt fuer alles (API fuer T1, UI fuer T2) |
| OC9 — Defense in Depth | Jeder Endpunkt braucht Auth, Plugins in Sandbox, Credentials sicher |
| OC10 — Orchestration > Model | Die AI ist nicht das Schwere. Das Zusammenbauen der APIs ist es. |

## Neu gelernt (aus Architektur-Analyse Mai 2026)

| Prinzip | Wie wir es nutzen |
|---|---|
| OC11 — Plugin-first Architecture | Model-Provider + Module sind externe Packages die dynamisch geladen werden. Core bleibt klein (~8MB bei OpenClaw). Fuer uns: T1-Module als Plugins, nicht als fest verdrahteter Code. |
| OC12 — Memory als Markdown + Hybrid-Index | OpenClaw speichert Memory als Plain Markdown auf Disk (YYYY-MM-DD.md + MEMORY.md). Dahinter: lokaler Hybrid-Index (Fulltext + Vektor). Fuer uns: Schicht 1-3 koennen plain files sein, Schicht 4 ist der Index darueber. |
| OC13 — Gateway als Daemon (Always-On) | Gateway laeuft dauerhaft als Hintergrund-Dienst (WebSocket :18789). Clients verbinden/trennen, Gateway bleibt. Fuer uns: unser Gateway sollte Daemon sein (systemd/Docker), nicht nur Request-Response. |
| OC14 — Monorepo mit klaren Package-Grenzen | `packages/core`, `packages/gateway`, `packages/agent`, `packages/sdk`, `packages/ui`. Jedes Package eigenstaendig deploybar. Fuer uns: Validiert unsere Struktur (src/core, src/gateway, src/modules, src/adapters). |
| OC15 — Skill-Registry (ClawHub) | Zentrale Registry wo Skills/Module gefunden und installiert werden. Fuer uns (spaeter): Modul-Marktplatz fuer T1-Entwickler. |

## Von NemoClaw (NVIDIA Security-Wrapper)

| Prinzip | Wie wir es nutzen |
|---|---|
| NC1 — Deny-by-Default | T1-Module starten mit NULL Rechten. Jeder Zugriff muss explizit freigeschaltet werden. Keine "open by default" Fehler moeglich. |
| NC2 — Privacy Router | Sensible Anfragen (Kundendaten, Zahlungen) gehen an lokale/eigene Modelle. Nur unkritische Anfragen gehen an Cloud-LLMs. Fuer uns: AI-Calls nach Daten-Sensitivitaet routen. |
| NC3 — Single-Command Onboarding | `nemoclaw onboard` richtet alles ein. Fuer uns: T2-Laden-Onboarding soll genauso simpel sein — ein Befehl/Flow und alles steht. |
| NC4 — Blueprint + Plugin Trennung | Plugin (TypeScript, duenn, CLI-Integration) vs. Blueprint (Python, Logik, Sandbox-Erstellung). Fuer uns: Adapter-Layer (duenn, Interface) vs. Service-Layer (Logik). |

## Von OpenShell (NVIDIA Sandbox-Runtime)

| Prinzip | Wie wir es nutzen |
|---|---|
| OS1 — Deklarative Policy (YAML) | Sandbox-Regeln als YAML definiert, nicht als Code. Lesbar, aenderbar, versionierbar. Fuer uns: T1-Modul-Berechtigungen als YAML-Config. |
| OS2 — 4 Schutzdomaenen | Filesystem (Landlock LSM), Netzwerk (OPA Proxy), Prozesse, Inferenz — jeweils eigene Isolation. Fuer uns: T1-Module koennen nur auf eigene Daten, eigene Endpoints, eigene Queue zugreifen. |
| OS3 — Live Policy Updates | Berechtigungen koennen zur Laufzeit erweitert/entzogen werden ohne Neustart. Fuer uns: Module koennen zur Laufzeit aktiviert/deaktiviert werden. |
| OS4 — Full Audit Trail | Jede Allow/Deny-Entscheidung wird geloggt. Forensik-Level. Fuer uns: Audit-Log fuer jeden API-Zugriff (wer, wann, was, erlaubt/verweigert). |
