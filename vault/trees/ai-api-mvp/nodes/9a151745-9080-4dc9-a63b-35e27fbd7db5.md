# T1 Developer API

## Ziel

T1-Entwickler sollen **sofort loslegen** koennen. Die 7 Schichten sind fertig. API-Key holen → bauen.

## Was T1 bekommt

- API-Key + Dokumentation
- Sandbox-Umgebung zum Testen
- Alle 7 AI-Readiness-Schichten fertig
- Zugriff auf Laden-Daten (mit Permission)
- Fertige Workflow-Bausteine (Booking, Chat, Recommend)
- Dashboard: Verbrauch, Kosten, Logs

## API-Design (T1-freundlich)

- Klar, konsistent, vorhersehbar
- Gute Fehlermeldungen
- Schnelle Responses
- Webhooks fuer Events
- SDKs (Python, Node.js)

## Plugin-Architektur (von OpenClaw OC11)

OpenClaw laedt Model-Provider und Module als **externe Packages dynamisch zur Laufzeit**. Der Core bleibt minimal.

Fuer uns:
- T1-Module sind eigenstaendige Packages mit definiertem Interface
- Module registrieren sich beim Gateway (wie OpenClaw-Plugins)
- Kein Rebuild des Kerns noetig wenn T1 ein Modul deployed
- SDK-Package (`packages/sdk`) definiert was ein Modul kann und muss

```
T1-Modul liefert:
├── manifest.yaml      ← Name, Version, Permissions, Hooks
├── routes.py          ← API-Endpunkte die registriert werden
├── service.py         ← Business-Logik
└── models.py          ← Datenmodell (eigene Tabellen)
```

## Sandbox fuer T1 (von NemoClaw NC1 + OpenShell OS1-OS4)

- **Deny-by-Default:** Modul startet mit null Rechten (NC1)
- **Deklarative Policy:** Berechtigungen als YAML, nicht als Code (OS1)
- **4 Schutzdomaenen:** Daten, Netzwerk, Queue, Inferenz — jeweils isoliert (OS2)
- **Live Updates:** Module koennen zur Laufzeit aktiviert/deaktiviert werden (OS3)
- **Audit Trail:** Jeder Zugriff wird geloggt — Allow UND Deny (OS4)

Konkret:
- Fremder Code laeuft in eigenem Prozess/Container
- Kann andere Module nicht beeinflussen
- Kann Plattform nicht kaputt machen
- Zugriff nur auf explizit freigegebene Daten und Endpoints
