# Projekt-Struktur (Claude-Code-freundlich)

## Prinzipien fuer Claude Code Wartbarkeit

1. **CLAUDE.md auf jeder Ebene** — Claude liest die naechste und kennt die Regeln fuer diesen Bereich
2. **Ein Modul = ein Ordner** — Claude mischt nie versehentlich Code zwischen Modulen
3. **Vorhersehbare Muster** — Jedes Modul hat dieselbe interne Struktur
4. **core/ ist heilig** — Geteilter Code den Module importieren, nie umgekehrt
5. **adapters/ isoliert externe APIs** — Stripe wechseln ohne Modul-Code anzufassen
6. **Tests spiegeln src/** — Sofort klar welcher Test was abdeckt

## Warum das fuer Claude Code funktioniert

| Prinzip | Effekt |
|---|---|
| CLAUDE.md pro Ordner | Claude weiss sofort: "In diesem Ordner darf ich nur X tun" |
| Ein Modul = ein Ordner | Claude aendert Booking und fasst Profile nicht an |
| core/ importiert man, aendert man selten | Claude bricht nicht alles wenn er ein Modul baut |
| adapters/ isoliert | Stripe-Aenderung hat null Effekt auf Module |
| Jedes Modul gleich aufgebaut | Claude erkennt das Muster und wiederholt es sauber |
| Tests neben Code | Claude weiss wo der Test hin muss |

## Die Regel fuer Claude

"Wenn du ein neues Modul baust, kopiere die Struktur von `modules/profile/` und passe sie an."

Das steht in `src/modules/CLAUDE.md` und Claude haelt sich dran.

## Validierung durch OpenClaw (OC14 — Monorepo-Struktur)

OpenClaw's Struktur (`packages/core`, `packages/gateway`, `packages/agent`, `packages/sdk`, `packages/ui`) bestaetigt unser Design:

| OpenClaw | Unsere Entsprechung | Funktion |
|---|---|---|
| packages/core | src/core/ | Datenmodell, Events, Keys |
| packages/gateway | src/gateway/ | Routing, Auth, WebSocket |
| packages/agent | src/memory/ + src/queue/ | AI-Runtime, Worker |
| packages/sdk | (spaeter) src/sdk/ | T1-Developer SDK |
| packages/ui | web/t2/ + web/t3/ | Frontend-Apps |

**Unterschied:** OpenClaw ist Node.js/TypeScript Monorepo (pnpm). Wir sind Python-Backend + Vue-Frontend. Aber die **Package-Grenzen** sind identisch — das ist das Entscheidende.
