# 4 Iterationen — Build-Reihenfolge

## Ueberblick

```
ITERATION 1        ITERATION 2        ITERATION 3        ITERATION 4
UMGEBUNG           KERN               MODULE             OBERFLAECHE
(Werkbank)         (Fundament)        (Features)         (was Nutzer sehen)

Einmal bauen,      Einmal bauen,      Modul-Loop         Waechst mit
immer nutzen       alle nutzen es     pro Feature        den Modulen
```

---

## Iteration 1 — UMGEBUNG [FERTIG]

Was: Die Werkbank auf der alles gebaut wird.
Wann: Einmal am Anfang.
Danach: Nie wieder anfassen (ausser Wartung alle 3 Monate).

Inhalt:
- Git + pre-commit Hooks (Ruff, pyright, gitleaks, pytest)
- CLAUDE.md + Memory + Session-Handoffs + Tree
- DevMonitor (Live-Flowchart)
- Health-Check
- Projekt-Struktur (Ordner-Skeleton)

---

## Iteration 2 — KERN

Was: Das Fundament auf dem alle Module stehen.
Wann: Einmal nach der Umgebung.
Danach: Selten aendern — nur wenn fundamental was fehlt.

Inhalt:
- Gateway (ein Eingang, Auth, Routing)
- Datenmodell + Structured Keys (shop_id Isolation)
- Queue pro Entity (Hintergrund-Jobs, isoliert)
- Memory 4 Schichten (Session, Daily, Longterm, Semantic)
- Event-System (Module kommunizieren darueber)
- Push-Infrastruktur
- Suche-Infrastruktur

---

## Iteration 3 — MODULE (Modul-Loop)

Was: Jedes Feature wird einzeln gebaut.
Wann: Immer wieder — jedes neue Feature durchlaeuft den Loop.
Danach: Feature ist live, naechstes Feature beginnt.

Inhalt: Alle Module die Laeden aktivieren koennen.
Reihenfolge: Booking zuerst (Tony), dann Payment, dann Rest.

→ Siehe "Modul-Loop" fuer den wiederkehrenden Prozess.

---

## Iteration 4 — OBERFLAECHE

Was: Was Nutzer tatsaechlich sehen und anfassen.
Wann: Waechst MIT den Modulen (Schritt 7 im Loop).
Danach: Wird mit jedem neuen Modul erweitert.

Inhalt:
- T3 Web-App (Endkunde: scannt QR, bucht, bezahlt)
- T2 Dashboard (Laden-Besitzer: sieht Buchungen, Kunden)
- T1 Developer Portal (API-Docs, Playground)
